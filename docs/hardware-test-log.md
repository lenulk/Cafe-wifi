# บันทึกผลการทดสอบบนฮาร์ดแวร์จริง (16–20 กันยายน 2026)

เอกสารนี้บันทึกผลการนำระบบขึ้นทดสอบบน Raspberry Pi จริงในห้องแล็บต่อเนื่อง 3 วันทำการ
ใช้เป็นข้อมูลสำหรับบทที่ 4 (ผลการทดลอง) และบทที่ 5 (สรุปและข้อจำกัด)

**หลักการที่ยึดตลอดการทดสอบ:** ผลลบของการทดสอบเครือข่ายต้องมีหลักฐานคู่ขนานยืนยันเสมอ
(เช่น `tcpdump` คู่กับ socket หรือ `conntrack -E` คู่กับฐานข้อมูล) เพราะเคยสรุปผิดมาแล้ว
จากการเชื่อผลลบที่ไม่มีหลักฐานประกอบ

## 3.1 ทดสอบกับเราเตอร์จริง TP-Link ER706W (20 ก.ย. 2026 เย็น)

เปลี่ยนจากการต่อตรงเข้าเครือข่ายแล็บ มาเป็นโครงสร้างแบบร้านจริง โดยใช้ **TP-Link ER706W
(Omada AX3000 Gigabit VPN Gateway)** แทนเราเตอร์บ้าน ทำให้ทดสอบข้อที่ค้างมาตั้งแต่ต้นโปรเจกต์ได้

**ผัง:** เน็ตแล็บ → WAN2 ของ ER706W (`172.20.18.140`) · วง `cafe-lan` VLAN 50 =
`192.168.50.0/24` **ปิด DHCP ปิด IPv6** · Pi `192.168.50.2` ต่อพอร์ต LAN4 (untagged VLAN 50) ·
โน้ตบุ๊คต่อ LAN3 · มือถือ/แท็บเล็ตต่อ SSID `Cafe-Guest` ของเราเตอร์ (ผูกกับวง cafe-lan) ·
ลูกค้าทุกเครื่องได้ `10.10.0.x` จาก Pi

| รายการ | ผล |
|---|---|
| ลูกค้าได้ IP จาก Pi (ไม่ใช่จากเราเตอร์) | ✅ โน้ตบุ๊ค `10.10.0.179` · แท็บเล็ต `10.10.0.212` ผ่าน Wi-Fi ของเราเตอร์ |
| captive portal | ✅ 307 ไปหน้า login |
| **IPv6 (ทดสอบครั้งแรก)** | ✅ **ไม่มี** — ดักฟัง Router Advertisement 40 วินาทีไม่พบสักแพ็กเก็ต และ Pi ไม่ได้ IPv6 global |
| ใช้งานหลัง login | ✅ HTTP 200 / HTTPS 200 ทั้งที่มี Access Control บังคับอยู่ |

### T16 — การข้าม portal ด้วยการตั้ง IP เอง (พิสูจน์ได้ทั้งสองด้าน)

ตั้งโน้ตบุ๊คเป็น `192.168.50.100/24 gw 192.168.50.1` (จำลองลูกค้าที่ตั้ง IP เองเพื่อเลี่ยง Pi)

| | ก่อนตั้ง Access Control | หลังตั้ง Access Control |
|---|---|---|
| `http://example.com` | **200 (ผ่าน)** | **000 (ถูกบล็อก)** |
| `https://www.google.com` | **200 (ผ่าน)** | **000 (ถูกบล็อก)** |
| ping `8.8.8.8` | สูญหาย 0% | สูญหาย 100% |
| ถูกบันทึกใน `conn_log`/`dns_log` | **0 แถว — ไม่มีหลักฐานเลย** | — |
| Pi ออกเน็ตได้ตามปกติ | ✅ | ✅ (200) |

กฎที่ใช้บนเราเตอร์ (Firewall → Access Control) เรียงลำดับสำคัญมาก:
1. **Allow** source = กลุ่มที่มีเฉพาะ `192.168.50.2` (Pi) · LAN → WAN · ALL
2. **Block** source = `192.168.50.0/24` · LAN → WAN · ALL

ถ้าสลับลำดับ Pi จะถูกบล็อกไปด้วยและทั้งร้านใช้เน็ตไม่ได้

### T17 — การตรวจจับ (ทดสอบกับอุปกรณ์แยกเครื่องจริงครั้งแรก)

ระหว่างที่เครื่องข้าม portal อยู่ `logger/bypass_detector.py` **ตรวจพบภายใน 1 นาที** บันทึก
`bypass_alert` (IP `192.168.50.100`, MAC ของเครื่องนั้น) และ `audit_log action=bypass_detected`
พร้อมระบุวง `192.168.50.0/24` ถูกต้อง — ยืนยันว่า N27 (อัปเดตค่าวงเครือข่ายเมื่อย้ายเครื่อง)
ทำงานจริง ถ้าไม่ได้แก้ไว้ ตัวตรวจจับจะยังเฝ้าวงแล็บเดิมแล้วมองไม่เห็นอะไรเลย

**สรุปตาม §3.1.4:** ชั้นที่ 4 (ตรวจจับ) ทำงานแต่ไม่ป้องกัน · ชั้นที่ 1 (Access Control ที่
เราเตอร์) ปิดช่องโหว่ได้ 100% ในการทดสอบนี้ · เราเตอร์ที่ไม่มีฟีเจอร์นี้จะเหลือแค่การตรวจจับ

### ข้อสังเกตระหว่างย้ายเครือข่าย

`install.sh` เคยตั้งค่าเครือข่าย**หลัง**ติดตั้งแพ็กเกจ เมื่อย้าย Pi ไปเครือข่ายใหม่ เครื่องจึงยัง
ใช้เส้นทางเก่าที่ใช้ไม่ได้แล้ว -> ค้างที่ pip นานหลายนาทีโดยไม่มีอะไรบอกสาเหตุ (preflight เตือนว่า
"ตรวจอินเทอร์เน็ตไม่ผ่าน" แต่ไม่ได้หยุดและไม่ได้แก้ให้) **แก้แล้วใน N37**: ถ้าออกเน็ตไม่ได้จริง
สคริปต์จะตั้ง IP + default route ของ uplink ให้ก่อนติดตั้งแพ็กเกจ และถ้าเน็ตใช้ได้อยู่แล้วจะไม่
แตะอะไรเลย · ทดสอบจริงจากสภาพ "eth0 ไม่มี IP และไม่มี default route" -> กู้เน็ตเองแล้วติดตั้งจบใน
2 นาที 11 วินาที pip ไม่ต้อง retry เลย

## 3.2 T6 — Client Isolation (ทดสอบ 20 ก.ย. 2026)

**สิ่งที่ค้นพบก่อนทดสอบ:** ไฟร์วอลล์บน Pi มีกฎกันลูกค้าคุยกันเองอยู่แล้ว
(`ip saddr $CLIENT_NET ip daddr $CLIENT_NET drop`) **แต่บังคับใช้ไม่ได้จริง** เพราะลูกค้า 2 เครื่อง
อยู่บน L2 เดียวกัน ทราฟฟิกระหว่างกันไม่เคยวิ่งผ่าน Pi — ยืนยันด้วยการวัด: โน้ตบุ๊ค (สาย)
ping แท็บเล็ต (ไร้สาย) สำเร็จ 100% ทั้งที่กฎมีอยู่ · ตรงกับที่ D9 ในแผนเตือนไว้ว่ามาตรการนี้
**ต้องทำที่เราเตอร์/AP เท่านั้น**

**ER706W ไม่มีตัวเลือกชื่อ "Client Isolation"** สิ่งที่ทำหน้าที่นี้คือช่อง **Guest Network**
ในหน้าตั้งค่า SSID ซึ่งคำอธิบายของ TP-Link เขียนว่า *"guest network will block clients from
reaching any private IP subnet"* — อ่านแล้วน่าจะบล็อก Pi (`10.10.0.1`) ไปด้วยจนระบบใช้ไม่ได้
**แต่ผลทดสอบจริงตรงข้าม**

| สิ่งที่วัด | ปิด Guest Network | เปิด Guest Network |
|---|---|---|
| ลูกค้า → ลูกค้า (`10.10.0.179` → `10.10.0.212`) | **ตอบกลับ 100%** | **สูญหาย 100% (ถูกบล็อก)** |
| ลูกค้า → Pi (`10.10.0.1`) | ✅ | ✅ ยังคุยได้ |
| หน้า portal | ✅ 307 | ✅ 307 |
| หลัง login: HTTP / HTTPS | ✅ | ✅ 200 / 200 |
| ลูกค้า → ลูกค้า หลัง login แล้ว | — | **ยังถูกบล็อก 100%** |

**สรุป:** ฟีเจอร์นี้ให้ผลตรงตามที่วัตถุประสงค์ O4 ต้องการ คือกันลูกค้าดักข้อมูลกันเองในวง LAN
ได้จริง โดยไม่กระทบการเข้าใช้งานผ่าน portal · **บทเรียน: ต้องทดสอบจริงเสมอ เพราะคำอธิบายใน
เอกสารของผู้ผลิตกับพฤติกรรมจริงไม่ตรงกัน**

**ข้อจำกัดของการทดสอบนี้:** วัดจากเครื่องต่อสาย → เครื่องไร้สาย (ซึ่งเป็นเส้นทางที่ผ่านทั้ง
สวิตช์ภายในและ AP) ยังไม่ได้วัดคู่ไร้สาย↔ไร้สายโดยตรง เพราะต้องสั่งการจากอุปกรณ์ลูกค้าทั้งสองฝั่ง
กลไกที่บล็อกเป็นตัวเดียวกัน (ตั้งที่ SSID) จึงคาดว่าให้ผลเหมือนกัน แต่ยังไม่ได้ยืนยันด้วยการวัด

### ก. ความเร็วที่เกตเวย์รองรับได้ (เป้า ≥ 200 Mbps)

วัดด้วยการดาวน์โหลดไฟล์ 300 MB ที่วางไว้ใน RAM ของ Pi (ไม่ใช้ microSD เพื่อไม่ให้ดิสก์เป็นคอขวด)
จากโน้ตบุ๊คฝั่งลูกค้า

| การวัด | ผล |
|---|---|
| สายเดียว 3 รอบ | **319.4 / 321.1 / 323.5 Mbit/s** |

ของระบบ** เพราะคอขวดอยู่ที่การ์ดแลน USB ของโน้ตบุ๊คที่ใช้ทดสอบ (ASIX USB 2.0 ซึ่งเพดานจริงราว
300 Mbit/s) ขณะที่ CPU ของ Pi แทบไม่ทำงาน

**เทียบความเร็วออกอินเทอร์เน็ตจากแหล่งเดียวกัน (ไฟล์ 50 MB จาก mirror.kku.ac.th):**

เข้า-ออกสายเส้นเดียวกัน = ทฤษฎีบอกว่าเหลือครึ่งหนึ่ง) เพราะในแล็บไม่มีเครื่องที่สองฝั่งนั้นให้ใช้

### ง. ความครบถ้วนของ log (เป้า ≥ 99% จาก 500 การเชื่อมต่อ)

สร้างการเชื่อมต่อ TCP ออกอินเทอร์เน็ต **500 ครั้ง** จากเครื่องลูกค้า เว้นระยะ ~8 ครั้ง/วินาที
(อัตราที่ใกล้เคียงการใช้งานจริงของร้าน) ปิดแบบบังคับ (RST) ทุกครั้งเพื่อให้ปิด session ทันที

| สิ่งที่วัด | ผล |
|---|---|
| เชื่อมต่อสำเร็จ | 500 / 500 |
| บันทึกลง `conn_log` | **500 แถว = 100%** (เกณฑ์ ≥99%) |
| พอร์ตต้นทางไม่ซ้ำกัน | 500 ค่า = ไม่มีการนับซ้ำ |
| MAC ที่บันทึก | ถูกต้องทุกแถว |
| `log_gap` ระหว่างทดสอบ | **ไม่มี** |

**ข้อสังเกต:** แถวแรกปรากฏใน DB ช้ากว่าการเชื่อมต่อจริงราว 30 วินาที (รอ conntrack ปิดรายการ)
— ตรงกับข้อจำกัดเรื่องความหน่วงที่บันทึกไว้แล้ว ไม่ใช่การสูญหาย
**ข้อควรบันทึก:** ระหว่างการทดสอบความเร็วช่วง 19:12 และ 19:19 พบ `log_gap` อย่างละ 1 ครั้ง
(ENOBUFS) ซึ่งเป็นช่วงรับส่งข้อมูลปริมาณมาก — ยังไม่ได้ไล่สาเหตุรายครั้ง แต่ยืนยันอีกครั้งว่าระบบ

## 3.4 การไล่หาต้นตอของหลักฐานที่หายไป (20 ก.ย. 2026 กลางคืน)

**จุดเริ่ม:** พบว่า `audit_log` มีแถว `log_gap` (ระบบแจ้งว่าเก็บหลักฐานได้ไม่ครบ) ประมาณ
5-9 ครั้งต่อชั่วโมง **ตลอดทั้งวัน** ไม่ใช่เฉพาะตอนทดสอบหนัก ทั้งที่แก้ N31 ไปแล้ว

**วิธีพิสูจน์ว่าหายจริงหรือแค่เตือนเกินจริง:** รันตัวฟังเหตุการณ์ตัวที่สองเป็น "ตัวอ้างอิง"
คู่ขนานกับระบบจริง แล้ว **เทียบพอร์ตต้นทางทีละรายการ** ระหว่างสิ่งที่ตัวอ้างอิงเห็นกับแถว
ที่ระบบบันทึกลงฐานข้อมูลได้

| รอบทดสอบ | ยิงไป | บันทึกได้ | ENOBUFS |
|---|---|---|---|
| ก่อนแก้ | 500 | 500 (100%) | ไม่เกิด |
| ก่อนแก้ | 300 | **283 (94.3%)** | เกิด 1 ครั้ง |
| ก่อนแก้ | 300 | **286 (95.3%)** | เกิด 2 ครั้ง |
| ก่อนแก้ | 150 | 150 (100%) | ไม่เกิด |
| **หลังแก้ N41** | 150 | **150 (100%)** | **ไม่เกิด** |

รายการที่หายมีเวลาห่างกันไม่ถึง 1 มิลลิวินาที = หายเป็นชุด ไม่ได้หายกระจาย และ**เกิดเฉพาะ
รอบที่มี ENOBUFS** ไม่ได้ขึ้นกับปริมาณทราฟฟิก

**สิ่งที่ตัดออกก่อนจะเจอต้นตอ** (บันทึกไว้เพื่อไม่ให้ใครเสียเวลาซ้ำ): ขนาดบัฟเฟอร์
(conntrack ตั้งได้ 64 MB อยู่แล้ว) · CPU (ว่าง 85-98%) · ARP หายชั่วคราว (สุ่ม 450 ครั้ง
ไม่หายเลย) · ตัวฟังตัวที่สองรบกวน · ข้อจำกัดทรัพยากรของ systemd (ไม่ได้ตั้งไว้)

**ต้นตอที่แท้จริง (N41):** เฝ้าเหตุการณ์ 13 นาทีแล้วนับรายวินาที พบชุดใหญ่ **250-290 รายการ
ในวินาทีเดียว ซ้ำทุก ~60-70 วินาที** ตรงกับรอบของตัวตรวจจับการข้าม portal (T17) พอดี ·
เปิดดูเนื้อหาของชุดนั้นพบว่าเป็น ICMP จาก Pi เองไปยัง 192.168.50.x ทั้งหมด
**= ฟีเจอร์ตรวจจับการโกงของเราเอง ไปทำลายหลักฐานของเราเอง**

ตัวตรวจจับยิง ping ทั้งวง 254 IP ทุกนาทีเพื่อบังคับให้เกิด ARP resolution เคอร์เนลจึงสร้าง
รายการติดตามการเชื่อมต่อ 254 รายการพร้อมกัน แล้ว**ตัวเก็บกวาดของเคอร์เนลลบทั้งหมดพร้อมกัน
ในรอบเดียว** (ทดลองแล้วว่าการทยอยยิงไม่ช่วย เพราะการลบเป็นรอบ ไม่ใช่ทีละรายการ)

**วิธีแก้:** สั่งไม่ให้ ICMP ที่ Pi ยิงเองในวง uplink ถูกติดตามตั้งแต่แรก (`notrack`) —
เป็นทราฟฟิกจัดการภายใน ไม่ใช่ข้อมูลจราจรของลูกค้าที่ ม.26 ต้องการอยู่แล้ว · ต้องเพิ่ม
กฎอนุญาต echo-reply ด้วย ไม่งั้นแพ็กเก็ตตอบกลับจะถูกทิ้งและการตรวจจับ (T17) จะเพี้ยน

**ผลหลังแก้:** จุดสูงสุดลดจาก 250-290 เหลือ **20-36 รายการต่อวินาที** · ICMP ในวง uplink
ที่เข้าระบบติดตาม = **0** · `ping` เราเตอร์ยังได้ผลตอบกลับครบ 100% (ยืนยันว่าไม่ทำ T17 พัง) ·
ทดสอบความครบถ้วนซ้ำได้ **150/150** โดยไม่มี ENOBUFS

> **บทเรียนที่ควรเขียนในเล่ม:** ระบบเฝ้าระวังที่ออกแบบมาเพื่อความปลอดภัย สามารถกลายเป็น
> ตัวทำลายหลักฐานเสียเองได้ ถ้าไม่ได้พิจารณาผลข้างเคียงที่มันสร้างต่อระบบเก็บ log ·
> และการที่ระบบ **บันทึกไว้เองว่าช่วงไหนเก็บได้ไม่ครบ** (`log_gap`) คือสิ่งเดียวที่ทำให้
> จับปัญหานี้ได้ ถ้าไม่มีกลไกนี้ หลักฐานจะหายไปเงียบ ๆ โดยไม่มีใครรู้

## 3.8 ทดสอบสภาพร้านจริง: สาย LAN เส้นเดียว (eth0) ไม่มี Wi-Fi ของ Pi (2 ต.ค. 2026)

ปิด wlan0 ของ Pi (`nmcli radio wifi off`) แล้วดูแลเครื่องผ่าน eth0 อย่างเดียว (โน้ตบุ๊กอยู่วงเดียวกัน 172.20.18.0/24)

- **บั๊กที่เจอ (N40):** Pi เอง resolve ชื่อไม่ได้ทันที — `install.sh` ตั้ง IP ของ eth0 เอง + ปลดจาก
  NetworkManager แต่**ไม่เคยตั้ง DNS ของ Pi** ที่ผ่านมาได้ DNS จาก DHCP ของ wlan0 มาตลอดจึงไม่เคยเห็น
  ผลกระทบ: หน้าสถานะขึ้น "ขาดการเชื่อมต่อ", ทดสอบความเร็วพัง และ**หลังรีบูต chrony จะหาเซิร์ฟเวอร์เวลา
  ไม่เจอ (เสี่ยงผิด ม.26)** · ลูกค้าไม่กระทบ (dnsmasq ส่งต่อ 1.1.1.1/8.8.8.8 ตรง ๆ)
- **แก้:** `configure_host_dns()` ใน install.sh — เขียน `/etc/resolv.conf` = `--host-dns` (ค่าเริ่มต้น
  1.1.1.1, 8.8.8.8) + NetworkManager `dns=none` กันเขียนทับ (หรือ drop-in ของ systemd-resolved ถ้าใช้) ·
  เรียกตั้งแต่ขั้นกู้เน็ตก่อนติดตั้งแพ็กเกจ (N37) · `netsetup.sh` เติมให้ทุกบูตถ้า resolv.conf ว่าง
- **ผล:** รัน install.sh ทับผ่าน eth0 อย่างเดียว exit 0 → **รีบูตทั้งที่ Wi-Fi ปิด**: บริการขึ้นครบ 8 ตัว,
  DNS ใช้ได้, chrony sync กับ time1.nimt.or.th (คลาด 0.0001 ms), หน้าสถานะ "เชื่อมต่อได้ ออกทาง eth0",
  ทดสอบความเร็ว 192.8/64.5 Mbps ปิง 46 ms, ลูกค้าจำลองขอใช้งาน→อนุมัติ→ออกเน็ตได้ (20 วิ หลังบูตใหม่),
  เข้า Admin จากโน้ตบุ๊กทาง eth0 ได้ · เปิด Wi-Fi กลับแล้ว resolv.conf ไม่ถูก NetworkManager เขียนทับ

## 3.9 พนักงานเข้าหน้าแอดมินจากวงลูกค้า (2 ต.ค. 2026 ค่ำ)

ร้านจริงมีแค่เราเตอร์ + Pi หลังปิด DHCP ของเราเตอร์ เครื่องพนักงานได้ IP วงลูกค้า (10.10.0.x) เหมือนทุกคน
แต่เดิมไฟร์วอลล์บล็อก :8443 จากวงลูกค้า (T8) → พนักงานเข้าหน้าแอดมินไม่ได้เลย · เจ้าของโครงงานเลือก
**เปิดหน้าแอดมินให้วงลูกค้า** + ปุ่ม "เข้าสู่ระบบสำหรับแอดมินและพนักงาน" บนหน้า portal

- **บั๊กที่เจอบนเครื่องจริง (N42):** เปิด nftables ของเราแล้วยังเข้าไม่ได้ — openNDS มี chain `ndsRTR` ของตัวเอง
  (users_to_router) อนุญาตแค่ udp 53/67, tcp 22/443 + พอร์ต portal แล้ว **reject ที่เหลือ** · แก้ด้วย
  `list users_to_router` ใน /etc/config/opennds — กำหนดเองแล้ว**แทนที่ค่าปริยายทั้งชุด** ต้องใส่ค่าเดิมกลับครบ
- **ผล (เครื่องลูกค้าจำลองที่ยังไม่ login portal = Preauthenticated):** หน้า portal มีปุ่ม ลิงก์ไป
  `https://cafe.wifi:8443/login` ✅ · login บัญชีพนักงานทดสอบได้ (302) ✅ · เปิดหน้าคำขอ/แดชบอร์ดได้ ✅ ·
  SSH จากวงลูกค้ายังถูกบล็อก ✅ · เครื่องนั้นยังออกเน็ตไม่ได้จนกว่าจะขอใช้งาน (307 ไป portal) ✅ ·
  audit บันทึก `login_ok ... ip=10.10.0.177` ✅ · ลูกค้าปกติยังขอใช้งาน→ออกเน็ตได้ (13 วิ) ✅
- **ป้องกันที่เพิ่ม:** จำกัดการเดารหัส 10 ครั้ง/10 นาที **ต่อชื่อผู้ใช้** (นอกจาก 5 ครั้งต่อ IP เดิม) เพราะลูกค้าเปลี่ยน IP ได้
- ความเสี่ยงที่ยอมรับ: ลูกค้าทุกคนเห็นหน้า login ของแอดมินได้ (ป้องกันด้วยรหัสผ่านรายคน + จำกัดการเดา + HTTPS + audit)

## 3.10 สำรองข้อมูลลง USB + ไล่ต้นตอ ENOBUFS ที่เหลือ (3 ต.ค. 2026)

**สำรองลง USB:** install.sh ตั้ง USB ที่ label `CAFEBACKUP` ให้ mount เองที่ `/mnt/cafebackup` (ไม่เสียบก็บูตได้)
ทดสอบด้วย USB จำลอง (ไฟล์ image ฟอร์แมต FAT ไม่ได้ฟอร์แมต USB จริงของใคร): ไม่เสียบ → backup ในเครื่องสำเร็จ
แต่เตือน "ไม่ได้เสียบ USB" และ**ไม่เขียนลง SD แทนเงียบ ๆ** · เสียบ → mount เอง คัดลอกสำเร็จ (gzip ถูกต้อง) ·
ถอด → เตือนอีกครั้ง · หน้าสถานะแสดงผลสำรองล่าสุด + สถานะ USB · วิธีเตรียม/กู้คืนอยู่ใน `docs/backup-usb.md`

**ENOBUFS ที่ยังเกิด 1-2 ครั้ง/วัน (N43):**
- `/proc/net/netlink` ของ socket conntrack: Drops เพิ่มเป็นชุด แต่ Rmem = 0 ตลอด = ตัวอ่านทันอยู่แล้ว
  ปัญหาคือ**ปริมาณเหตุการณ์เป็นชุดใหญ่** ไม่ใช่ตัวอ่านช้า
- `nf_conntrack_count` ลดฮวบ ~250 ทุก ~60 วินาที (หมดอายุพร้อมกัน) · `conntrack -L` พบ **122 จาก 281 รายการ
  เป็นการเชื่อมต่อ MariaDB ภายในเครื่อง** (127.0.0.1:3306 — ทุกบริการเปิดใหม่ทุก query) ไม่ใช่ทราฟฟิกลูกค้าเลย
- อีกราวครึ่งของเหตุการณ์ที่เหลือเป็นทราฟฟิกของ Pi เอง (dnsmasq ถาม 1.1.1.1 ทุกครั้งที่ลูกค้าถาม DNS, chrony)
- **แก้ 2 ชั้น:** (1) nftables `iif/oif lo notrack` — loopback ไม่ถูกติดตามเลย (2) ตัวเก็บใช้
  `conntrack -E -s 10.10.0.0/24` ให้เคอร์เนลกรองด้วย BPF ที่ socket เหลือแค่เหตุการณ์ของวงลูกค้า
- **ผล:** loopback ในตาราง 116 → 0, ตารางรวม ~280 → ~56 ตอนไม่มีลูกค้า, netlink drops = 0,
  บริการที่ใช้ DB ไม่มี error · **ทดสอบความครบถ้วน 323/323 (ไม่หายเลย) ไม่มี ENOBUFS** เทียบตัวฟังอ้างอิงที่ไม่กรอง
- ข้อจำกัด: ENOBUFS เดิมเกิดแค่ 1-2 ครั้ง/วัน ต้องเฝ้าต่ออีกอย่างน้อย 1 วันจึงสรุปได้ว่าหายจริง

## 5. ข้อจำกัดที่ยืนยันด้วยการวัดจริง (ใช้ในบทที่ 5)

1. **การเก็บ log แบบอิงเหตุการณ์มีโอกาสสูญหายเมื่อมีเหตุการณ์จบพร้อมกันจำนวนมาก**
   สาเหตุหลักที่เคยทำให้หายจริง (ping สำรวจวงของระบบเอง) แก้แล้วใน N41 และทดสอบซ้ำได้
   ครบ 100% แต่ **ข้อจำกัดเชิงกลไกยังอยู่**: ถ้ามีเหตุการณ์จบพร้อมกันมากพอ (เช่น สร้าง
   3,000 การเชื่อมต่อใน 26 วินาที) ยังมีโอกาสล้นได้ · **ระบบบันทึกช่วงที่หลักฐานอาจไม่ครบ
   ไว้เอง** (`audit_log action=log_gap`) ซึ่งเป็นสิ่งเดียวที่ทำให้จับ N41 ได้ ·
   แนวทางในอนาคต: ตรวจทานกับ `conntrack -L` เป็นระยะ หรือย้ายไปใช้ NFLOG/IPFIX
2. **โควตาถูกบังคับช้ากว่าการใช้งานจริงราว 2 นาที** ลูกค้าจึงใช้เกินโควตาได้เล็กน้อยเสมอ
3. **เวลาปิด session ไม่ใช่เวลาที่ลูกค้าเดินออกจากร้าน** ระบบปิดเมื่อตรวจพบว่าไม่อยู่ในระบบแล้ว
   (ตรวจทุก 5 นาที) หรือเมื่อ voucher หมดสิทธิ์ · เวลาใช้งานจริงดูได้จาก `conn_log`
4. **Pi 4 ไม่มีนาฬิกา RTC** ถ้า NTP ติดต่อไม่ได้หลังไฟดับ ระบบจะเปิดให้บริการโดยที่นาฬิกายังผิด
   (เลือกให้ร้านใช้งานได้ ดีกว่าปิดร้าน) ทางแก้ถาวรคือติดโมดูล RTC ภายนอก · ตั้งแต่ 2 ต.ค. 2026
   ติดตั้ง `fake-hwclock` แล้ว ความคลาดเคลื่อนช่วงนั้นจึงเหลือเท่ากับระยะเวลาที่ไฟดับ (เดิมย้อนไปถึงวันที่
   แฟลชเครื่อง)
5. **ช่องโหว่การตั้ง IP เองเพื่อข้าม portal มีอยู่จริงและวัดได้แล้ว** (ดู §3.1) ถ้าเราเตอร์ไม่มี
   Access Control ลูกค้าตั้ง IP เองแล้วออกเน็ตได้ทันทีโดยไม่มีหลักฐานใด ๆ · เราเตอร์ที่มีฟีเจอร์นี้
   (ทดสอบกับ TP-Link ER706W) ปิดช่องโหว่ได้ 100% · **ข้อกำหนดขั้นต่ำของเราเตอร์ที่จะนำไปใช้จริง
   จึงต้องมี Access Control หรือ ACL ระดับ LAN→WAN**
6. **ระบบรองรับเฉพาะ IPv4** ทดสอบแล้วว่าเมื่อปิด IPv6 ที่เราเตอร์ จะไม่มี IPv6 เล็ดลอดเข้ามาจริง
   (ดักฟัง Router Advertisement 40 วินาทีไม่พบสักแพ็กเก็ต — §3.1) · **แต่ถ้าเราเตอร์เปิด IPv6 ไว้
   ทราฟฟิก IPv6 จะข้าม portal และไม่ถูกบันทึกเลย** จึงเป็นข้อกำหนดบังคับว่าต้องปิด IPv6 ที่เราเตอร์
   ก่อนใช้งานจริง (ดู §3.1.3 ข้อ 7) ยังไม่ได้ทดสอบกรณีเปิด IPv6 ไว้ว่ารั่วมากน้อยแค่ไหน
7. **สำรองข้อมูลอยู่บน microSD ใบเดียวกับระบบ** ยังไม่ได้ตั้งค่าสำรองออกนอกเครื่อง
8. **ขอบเขตการทดสอบจำกัดอยู่ที่ Windows และ Android** — iOS/macOS และการใช้งานพร้อมกัน
   หลายเครื่อง (T14) ตัดออกตามการตัดสินใจเพราะไม่มีอุปกรณ์ · ผลที่รายงานในเล่มจึงครอบคลุม
   เฉพาะสองระบบปฏิบัติการนี้ และ **ไม่ควรอ้างว่าใช้ได้กับ iOS โดยไม่มีการทดสอบ**
9. **เวลา login ไม่ผ่านเกณฑ์ที่ตั้งไว้เอง** วัดได้ 3.90 วินาที (เป้า ≤3) โดย 85% ของเวลาอยู่ใน
   openNDS ซึ่งสั่งงาน nftables ผ่านเชลล์สคริปต์ — ยืนยันด้วยการจับเวลา `ndsctl auth` ตรง ๆ ได้
   1.86–2.12 วินาที · ส่วนของโครงงานเอง (ตรวจรหัส + บันทึก session) ใช้เพียง 0.35 วินาที (§3.3 ค)
10. **ยังไม่ได้วัดความเร็วกรณีรับส่งเข้า-ออกสายเส้นเดียวกัน** (ลูกค้าคุยกับเครื่องในฝั่งอัปลิงก์)
   ซึ่งตามทฤษฎีจะเหลือประมาณครึ่งหนึ่ง เพราะแล็บไม่มีเครื่องที่สองในฝั่งนั้น (§3.3 ก)
