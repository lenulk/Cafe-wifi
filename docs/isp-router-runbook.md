# คู่มือย้ายระบบไปใช้กับเราเตอร์ของค่ายอินเทอร์เน็ต

เอกสารนี้ใช้ตอนย้าย Pi จากแล็บ/ER706W ไปต่อกับเราเตอร์ที่ค่ายเน็ตแถมมาที่บ้าน
(ทดสอบความเสี่ยง **R12** ของโครงงาน) เขียนจากบทเรียนจริงที่เจอมาแล้วทุกข้อ

> **หลักการที่ต้องถือตลอด:** ผลลบของการทดสอบเครือข่ายต้องมีหลักฐานคู่ขนานเสมอ
> (`tcpdump` / ตัวนับ / log) ห้ามสรุปจากสิ่งที่เห็นบนเบราว์เซอร์อย่างเดียว

---

## ขั้นที่ 0 — สำรวจเราเตอร์ก่อน (ทำก่อนถอดสายใด ๆ ทั้งสิ้น)

เข้าหน้าเว็บของเราเตอร์แล้วหาให้ครบ 7 ข้อ **จดลงตารางนี้ไว้ใช้เขียนเล่ม**

| # | สิ่งที่ต้องหา | ชื่อที่อาจใช้ในเมนู | มี/ไม่มี | ถ้าไม่มี |
|---|---|---|---|---|
| 1 | ตั้ง LAN IP ได้ | LAN Setup, Network | | ใช้ค่าเดิมได้ แต่ต้องจด |
| 2 | **ปิด DHCP ได้** | DHCP Server | | จำกัด pool ให้เหลือ 1-2 IP แล้วกันไว้ให้ Pi |
| 3 | ตั้ง SSID + รหัสผ่านได้ | Wireless | | — |
| 4 | **Client / AP Isolation** | AP Isolation, Guest Network, Client Isolation | | O4 อ่อนลง ต้องเขียนเป็นข้อจำกัด |
| 5 | **Access Control (LAN→WAN)** | Access Control, IP Filtering, Parental Control, Firewall Rules, MAC Filter | | ช่องโหว่ bypass เปิดกว้าง (ข้อจำกัดสำคัญที่สุด) |
| 6 | ปิด UPnP ได้ | UPnP | | ความเสี่ยงเพิ่มเล็กน้อย |
| 7 | **ปิด IPv6 ฝั่ง LAN ได้** | IPv6, RA, SLAAC, DHCPv6 | | **ช่องโหว่ที่ใหญ่ที่สุด** ทราฟฟิก IPv6 จะข้าม portal ทั้งหมด |

**ข้อ 4 มีกับดัก:** เราเตอร์บางยี่ห้อ "Guest Network" จะตัดขาดจากวง LAN ทั้งหมด ซึ่งจะทำให้
ลูกค้าคุยกับ Pi ไม่ได้เลย = ระบบใช้ไม่ได้ · บางยี่ห้อ (ทดสอบแล้วกับ TP-Link ER706W) กันเฉพาะ
ลูกค้าคุยกันเองแต่ยังถึง Pi ได้ = ใช้ได้ · **ต้องทดสอบจริงเสมอ ห้ามเชื่อคำอธิบายในเมนู**
ถ้าใช้ Aruba AP-515 ในแล็บ ให้ตั้ง Client IP assignment เป็น **Network assigned** (bridge)
และเปิด client isolation ของ SSID; ห้ามใช้ Virtual Controller assigned เพราะ AP จะ NAT ลูกค้า
หลัง IP/MAC ของตนเอง ผล client isolation บน Aruba ยังต้องทดสอบจริงแยกจาก ER706W

## ขั้นที่ 1 — ตั้งค่าเราเตอร์ (ยังไม่ต้องต่อ Pi)

1. จด LAN IP ของเราเตอร์ เช่น `192.168.1.1/24` → วง uplink คือ `192.168.1.0/24`
2. เลือก IP ให้ Pi ที่อยู่นอกช่วง DHCP เดิม เช่น `192.168.1.2`
3. **ปิด DHCP ของเราเตอร์** (ถ้าไม่ปิด ลูกค้าจะได้ IP จากเราเตอร์แทน Pi = ข้าม portal ทั้งหมด)
4. **ปิด IPv6 ฝั่ง LAN**
5. ตั้ง SSID สำหรับลูกค้า + เปิด Client Isolation (ถ้ามี) แล้วทดสอบว่าลูกค้า 2 เครื่องคุยกันไม่ได้
   ขณะที่แต่ละเครื่องยังเข้า Pi/portal ได้ (แยกผลทดสอบ Wi-Fi↔Wi-Fi และสาย↔Wi-Fi ถ้ามีทั้งสองแบบ)
6. ยังไม่ต้องตั้ง Access Control — **จะตั้งทีหลังเพื่อให้ทดสอบ T16 ได้ทั้งสองด้าน**

## ขั้นที่ 2 — ย้าย Pi (ลำดับนี้เท่านั้น ไม่งั้น SSH หลุด)

> **เตือน:** ขั้นนี้ทำให้เน็ตของเครื่องที่ใช้ทดสอบหลุดชั่วคราว · ถ้าจะ SSH ต้องแน่ใจว่ายังมี
> เส้นทางจัดการอื่น (Wi-Fi ของ Pi หรือจอ+คีย์บอร์ด) ก่อนเริ่ม

```bash
# 1) ต่อสาย Pi เข้าเราเตอร์ตัวใหม่ แล้วเข้าไปที่เครื่อง Pi (จอ+คีย์บอร์ด หรือ Wi-Fi ของ Pi)
# 2) ตั้งค่าเครือข่ายชั่วคราวให้มีเน็ตก่อน (install.sh รุ่นใหม่ทำให้อัตโนมัติแล้ว -- N37)
sudo ip addr flush dev eth0
sudo ip addr add 192.168.1.2/24 dev eth0
sudo ip link set eth0 up
sudo ip route replace default via 192.168.1.1 dev eth0
ping -c2 1.1.1.1
```

จากนั้นรันตัวติดตั้งซ้ำด้วยค่าเครือข่ายใหม่ (ข้อมูลเดิมทั้งหมดยังอยู่ ไม่ได้ลบ):

```bash
cd ~/cafe-wifi && sudo ./install.sh -y --nic eth0 --uplink-cidr 192.168.1.2/24 --uplink-gw 192.168.1.1
```

**ภายใน 5 นาทีหลังรันเสร็จ ต้องยกเลิกสวิตช์กันตาย ไม่งั้นไฟร์วอลล์จะถูกล้าง:**

```bash
sudo systemctl stop cafe-wifi-nft-failsafe.timer
```

แล้ว **รีบูต 1 ครั้ง** เพื่อให้ IP ของเครือข่ายเก่าหลุดออกจาก `eth0` และพิสูจน์ว่าทุกอย่างกลับมาเอง

## ขั้นที่ 3 — ตรวจ 7 ข้อหลังย้าย (ใช้เวลา ~15 นาที)

| # | ตรวจอะไร | คำสั่ง / วิธี | ผลที่ต้องได้ |
|---|---|---|---|
| 1 | บริการครบ | `systemctl --failed` | ต้องว่าง |
| 2 | ลูกค้าได้ IP จาก **Pi** | ต่อเครื่องเข้า SSID แล้วดู IP | ต้องเป็น `10.10.0.x` ไม่ใช่วงของเราเตอร์ |
| 3 | portal เด้ง | `curl --interface <ip ลูกค้า> -s -o /dev/null -w "%{http_code} %{redirect_url}" http://example.com/` | `307` ไปหน้า login |
| 4 | login แล้วใช้เน็ตได้ | login ด้วย voucher จริง | HTTP/HTTPS 200 |
| 5 | **IPv6 ไม่รั่ว** | `sudo tcpdump -ni eth0 -c 5 icmp6 and ip6[40]==134` (รอ 60 วิ) | **ต้องไม่มีแพ็กเก็ต** และมือถือต้องไม่มี IPv6 |
| 6 | **T16 ก่อนตั้ง ACL** | ตั้ง IP เองบนเครื่องทดสอบเป็น `192.168.1.50/24 gw 192.168.1.1` แล้วลองออกเน็ต | ออกได้ = ยืนยันช่องโหว่ (บันทึกไว้) |
| 7 | **T16 หลังตั้ง ACL** | ตั้ง Access Control ให้ออก WAN ได้เฉพาะ IP ของ Pi | ต้องออกไม่ได้ ส่วน Pi และลูกค้าที่ login แล้วยังปกติ |

**T17 (ตรวจจับการ bypass)** — ระหว่างทำข้อ 6 ให้รอ 1-2 นาที แล้วดูว่าระบบจับได้ไหม:

```bash
mysql cafewifi -e "SELECT ts, ip, mac, detail FROM bypass_alert ORDER BY id DESC LIMIT 5;"
```

**T6 (client isolation)** — ต่อลูกค้า 2 เครื่อง แล้ว ping กันเอง: ก่อนเปิดฟีเจอร์ต้องได้ หลังเปิดต้องไม่ได้
และต้องตรวจด้วยว่าหลังเปิดแล้ว **ยังเข้า portal และใช้เน็ตหลัง login ได้**

## ขั้นที่ 4 — บันทึกผลลงเล่ม

เขียนลง `docs/hardware-test-log.md` หัวข้อใหม่ โดยระบุให้ครบ:
- ยี่ห้อ/รุ่นเราเตอร์ และค่ายเน็ต
- ตาราง 7 ข้อจากขั้นที่ 0 (มี/ไม่มีอะไรบ้าง)
- ผลตรวจ 7 ข้อจากขั้นที่ 3 พร้อมตัวเลขจริง
- **ถ้าเราเตอร์ขาดฟีเจอร์ใด ให้เขียนตรง ๆ ว่าข้อจำกัดคืออะไร** ไม่ต้องกลบ —
  ผลที่ว่า "เราเตอร์ที่ค่ายเน็ตแถมมาใช้ไม่ได้ครบทุกมาตรการ" เป็นข้อค้นพบที่มีค่าสำหรับเล่ม
  มากกว่าการทดสอบเฉพาะกับเราเตอร์ราคาแพงที่มีฟีเจอร์ครบ

| อาการ | สาเหตุที่เคยเจอจริง | ทางแก้ |
|---|---|---|
| ติดตั้งค้างนานที่ขั้นดาวน์โหลดแพ็กเกจ | เส้นทางออกเน็ตเดิมตายแล้ว | ทำขั้นที่ 2 ข้อ 2 ก่อนเสมอ |

| ลูกค้าได้ IP วงเราเตอร์ | ข้อ 3 ของขั้นที่ 1 ยังไม่ได้ทำ | ปิด DHCP ที่เราเตอร์ |
| เข้าหน้าแอดมินไม่ได้ | ต่อ Wi-Fi ร้านแล้วพิมพ์ **`https://admin.cafe.wifi`** (ต้องพิมพ์ `https://` เอง — แบบ http ถูก openNDS ดักไปหน้า portal) · ทางสำรอง `https://cafe.wifi:8443` | หน้า portal ของลูกค้าไม่มีปุ่ม/ลิงก์ไปหน้าแอดมิน (เอาออก 3 ต.ค. 2026) · รหัสผ่านรายคน + จำกัดการเดารหัส |

| SSH เข้า Pi ไม่ได้หลังย้าย | พอร์ต 22 ถูกปิดสำหรับวงลูกค้า | ต่อจากฝั่ง uplink หรือใช้ Wi-Fi ของ Pi |
